# 标题

## 2026年9月26日

今天的内容可以围绕一个核心问题串起来：**怎样把软件做出来，并让它在使用和变化中持续满足要求？**

先看骨架，再顺着因果理解。这里是今天内容的回忆树，不是完整的软件工程分类。

```
怎样让软件持续满足要求？
├─ 建造时：怎样组织开发过程？
│  └─ 需求明确、技术成熟 → 瀑布模型是候选
└─ 使用和演进时：怎样判断“做得好”？
   ├─ 当前服务
   │  ├─ 响应够不够快？ → 性能
   │  └─ 服务是否持续可用？
   │     ├─ 能否持续无故障？ → 可靠性
   │     └─ 需要时能否使用？ → 可用性
   └─ 未来变化
      └─ 改动是否容易、影响范围是否可控？ → 可修改性
         └─ 你的项目实践：按职责拆分代码
```

**第一条线：需求稳定，为什么适合瀑布模型？**

瀑布模型把开发组织为需求分析、设计、编码、测试等阶段，前一阶段的成果为后一阶段提供依据。

这意味着：**越靠前的决定发生变化，越可能影响后面已经完成的工作。**例如需求改了，设计、代码和测试都可能需要跟着改。因此，需求明确、技术成熟时，采用这种阶段式推进方式比较合适。

你的题目还给出“各阶段完成后提交文档并评审”，这与它的阶段管理方式相符。

边界要记准：**瀑布不是绝对不能回头，而是回头修改通常代价较大。**需求频繁变化时，可以考虑敏捷方式，但今天还没有系统学习敏捷。

**第二条线：“软件好用”为什么必须拆成具体要求？**

“好用”没有说明关注什么，也没有说明达到什么程度才算合格。把它转成具体场景和指标，才能设计、测试和验收。

|今天的概念|它回答什么问题|今天的例子|
|---|---|---|
|性能|在给定负载下，响应速度、处理能力怎么样？|挂号请求在 2 秒内返回|
|可靠性|在规定条件和时间内，能否持续无故障运行？|连续一个月无故障|
|可用性|需要服务时，系统能否提供服务？|故障后 30 秒内恢复挂号|

可靠性与可用性容易混淆，因为它们确实存在因果联系：

**故障少 → 中断机会少；恢复快 → 每次中断时间短。两者都有助于提高可用性。**

所以，“恢复快”是改善可用性的一条路径，不能把可用性直接定义成“恢复速度”。你后来已经能正确区分“一个月无故障”和“几秒内恢复”。

**第三条线：为什么拆分职责，可能让软件更容易修改？**

你原来的项目把运算逻辑和界面处理混在一起。这样的结构容易让一次算法修改牵涉界面代码，也使定位问题更费力。

你的改造是：

```
原问题：运算与界面逻辑混杂
    ↓
做法：区分数据结构、功能运算、界面更新职责
      再按软件功能模块组织到不同类中
    ↓
观察到的效果：新增功能和调试更方便
```

它主要对应**可修改性**：完成一次修改需要多少工作，影响多少地方。

但真正起作用的是**职责和依赖关系变清楚**，并非“类越多越好”。如果拆开后仍然互相依赖内部细节，修改仍可能到处传播。因此，我们暂时不能仅凭拆分类，就宣布已经实现低耦合，或直接称它为 MVC。

你对“更换算法”的分析也可以整理成一个条件判断：

- **只改变内部计算方法，输入输出及用户操作不变**：尽量把修改限制在运算部分。
- **新算法需要新的参数、操作或结果展示**：UI，也就是用户界面，可以相应修改。
- **现有数据结构仍能表达所需数据**：可以保持不变；不能表达时才需要调整。

这里的目标是：**让必要的地方改变，避免变化无故蔓延。**

这段真实经历也成为了今天的论文素材：**问题 → 做法 → 效果**。目前有定性效果，后续再补一个具体修改实例，不编造效率数字。

今天已确认：你能在讲解后判断瀑布适用场景、区分可靠性与可用性，并结合项目分析修改影响。**隔天能否独立回忆仍需验证；综合、案例、论文的完整应试水平目前均未测量。**

明天闭卷回顾时，只问自己一个问题：**“软件从建造、运行到修改，我分别要关心什么？”**先长出分支，再补术语和原因；卡在哪一处，就复习那一处。

最后用这句话把整棵树收起来：

**“先看需求稳不稳，决定怎么做；再看运行快不快、能稳多久、出故障多久能用；以后要改，就让变化尽量留在该改的地方。”**
