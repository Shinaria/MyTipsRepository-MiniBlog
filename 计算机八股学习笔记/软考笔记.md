
# 2026年9月26日

今天的内容可以围绕一个核心问题串起来：**怎样把软件做出来，并让它在使用和变化中持续满足要求？**

先看骨架，再顺着因果理解。这里是今天内容的回忆树，不是完整的软件工程分类。

```
怎样让软件持续满足要求？
├─ 建造时：怎样组织开发过程？
│  └─ 需求明确、技术成熟 → 瀑布模型是候选
└─ 使用和演进时：怎样判断“做得好”？
   ├─ 当前服务
   │  ├─ 响应够不够快？ → 性能
   │  └─ 服务是否持续可用？
   │     ├─ 能否持续无故障？ → 可靠性
   │     └─ 需要时能否使用？ → 可用性
   └─ 未来变化
      └─ 改动是否容易、影响范围是否可控？ → 可修改性
         └─ 你的项目实践：按职责拆分代码
```

**第一条线：需求稳定，为什么适合瀑布模型？**

瀑布模型把开发组织为需求分析、设计、编码、测试等阶段，前一阶段的成果为后一阶段提供依据。

这意味着：**越靠前的决定发生变化，越可能影响后面已经完成的工作。**例如需求改了，设计、代码和测试都可能需要跟着改。因此，需求明确、技术成熟时，采用这种阶段式推进方式比较合适。

你的题目还给出“各阶段完成后提交文档并评审”，这与它的阶段管理方式相符。

边界要记准：**瀑布不是绝对不能回头，而是回头修改通常代价较大。**需求频繁变化时，可以考虑敏捷方式，但今天还没有系统学习敏捷。

**第二条线：“软件好用”为什么必须拆成具体要求？**

“好用”没有说明关注什么，也没有说明达到什么程度才算合格。把它转成具体场景和指标，才能设计、测试和验收。

|今天的概念|它回答什么问题|今天的例子|
|---|---|---|
|性能|在给定负载下，响应速度、处理能力怎么样？|挂号请求在 2 秒内返回|
|可靠性|在规定条件和时间内，能否持续无故障运行？|连续一个月无故障|
|可用性|需要服务时，系统能否提供服务？|故障后 30 秒内恢复挂号|

可靠性与可用性容易混淆，因为它们确实存在因果联系：

**故障少 → 中断机会少；恢复快 → 每次中断时间短。两者都有助于提高可用性。**

所以，“恢复快”是改善可用性的一条路径，不能把可用性直接定义成“恢复速度”。你后来已经能正确区分“一个月无故障”和“几秒内恢复”。

**第三条线：为什么拆分职责，可能让软件更容易修改？**

你原来的项目把运算逻辑和界面处理混在一起。这样的结构容易让一次算法修改牵涉界面代码，也使定位问题更费力。

你的改造是：

```
原问题：运算与界面逻辑混杂
    ↓
做法：区分数据结构、功能运算、界面更新职责
      再按软件功能模块组织到不同类中
    ↓
观察到的效果：新增功能和调试更方便
```

它主要对应**可修改性**：完成一次修改需要多少工作，影响多少地方。

但真正起作用的是**职责和依赖关系变清楚**，并非“类越多越好”。如果拆开后仍然互相依赖内部细节，修改仍可能到处传播。因此，我们暂时不能仅凭拆分类，就宣布已经实现低耦合，或直接称它为 MVC。

你对“更换算法”的分析也可以整理成一个条件判断：

- **只改变内部计算方法，输入输出及用户操作不变**：尽量把修改限制在运算部分。
- **新算法需要新的参数、操作或结果展示**：UI，也就是用户界面，可以相应修改。
- **现有数据结构仍能表达所需数据**：可以保持不变；不能表达时才需要调整。

这里的目标是：**让必要的地方改变，避免变化无故蔓延。**

这段真实经历也成为了今天的论文素材：**问题 → 做法 → 效果**。目前有定性效果，后续再补一个具体修改实例，不编造效率数字。

今天已确认：你能在讲解后判断瀑布适用场景、区分可靠性与可用性，并结合项目分析修改影响。**隔天能否独立回忆仍需验证；综合、案例、论文的完整应试水平目前均未测量。**

明天闭卷回顾时，只问自己一个问题：**“软件从建造、运行到修改，我分别要关心什么？”**先长出分支，再补术语和原因；卡在哪一处，就复习那一处。

最后用这句话把整棵树收起来：

**“先看需求稳不稳，决定怎么做；再看运行快不快、能稳多久、出故障多久能用；以后要改，就让变化尽量留在该改的地方。”**

# 2026年9月27日：怎样确认需求，并验证软件满足要求？

## 一、开发之前：先弄清“要做什么”

### 1. 需求明确、较稳定：可以考虑瀑布模型

按“需求分析 → 设计 → 编码 → 测试”等阶段推进，前一阶段的成果为后一阶段提供依据。

**为什么后期改需求通常更贵？**后续成果已经依据旧需求完成，旧前提改变，可能引发设计、代码和测试的返工。

### 2. 需求说不清：用原型帮助澄清

原型是用于探索或验证想法的初步模型、简化版本。

**需求模糊 → 制作原型 → 用户体验 → 具体反馈 → 明确需求。**

做出界面是手段，弄清需求才是目的。示例数据可以帮助确认字段和操作方式，但不能据此证明正式系统的性能。客户提出修改意见，可能恰好说明原型发挥了作用。

## 二、发生变化：先判断“哪些地方受影响”

### 1. 依赖关系决定修改范围

需求改变后，应检查依赖它的成果：

- **仍然适用：**保留、复用。
- **不再适用：**修改或重新实现。

“都要检查”不等于“全部重做”。例如批量处理可以逐个调用原有单样本算法，不一定需要改写算法。

### 2. 保留代码，也要验证

外围代码变化可能影响原有功能。**回归测试**就是在修改后，检查原来正常的功能是否受到破坏；可以复用已有测试，不等于重写全部测试。

## 三、验证结果：分清“到底验证了什么”

### 1. 用户要不要：需求确认

用户认可报表字段和筛选方式，说明这部分需求得到确认，不能直接推断性能或可靠性达标。

### 2. 系统做得怎么样：分别判断

- **功能正确性：**结果是否正确。
- **性能：**在给定负载下，响应速度、处理能力是否满足要求。
- **可靠性：**在规定条件和时间内，能否持续无故障。
- **可用性：**需要时能否提供服务；故障频率和恢复时间都会影响它。
- **可修改性：**修改成本多大、影响范围多广。

一次结果正确不能证明长期可靠；没有故障也不能抵消响应超时。

### 3. 把要求变成可判断的标准

**质量属性 → 度量指标 → 达标阈值**

例如：**性能 → 响应时间 → 不超过 1 秒。**  
属性说明关注什么，指标说明怎样衡量，阈值说明怎样才算合格。

**回忆线索：先弄清要什么；变化时顺着依赖查影响；验证时分清对不对、快不快、能否持续正常工作。**

# 2026年9月30日：怎样让修改少牵连、运行少耗时？

## 一、开发前：用原型明确需求

### 1. 原型的目的

需求细节说不清时，先提供可体验的版本，让用户给出具体反馈，再完善需求。仍需有初步目标和范围。

**需求模糊 → 原型体验 → 具体反馈 → 需求明确。**

### 2. 验证结论有边界

客户认可字段和操作方式，说明这部分需求得到确认；不能由此推断系统运行速度或长期稳定性达标。

## 二、组织代码：让变化尽量留在必要范围

### 1. 划分职责——高内聚

把围绕同一任务、因同类原因变化的代码集中起来，把不同变化来源分开。

你的项目可以分为：**文件读取 → 反序列化 → 界面显示**。文件来源、数据格式、显示样式可能分别变化，因此分开有助于限制修改范围。

### 2. 组织依赖——低耦合

模块通过明确接口协作，隐藏内部实现。调用方依赖必要的输入输出约定，不直接操纵对方内部细节。

**接口及其含义不变 → 内部实现可以调整 → 调用方可能无需修改。**

这主要改善**可修改性**，但不保证所有变更都互不影响。

### 3. 观察调用结构——扇入与扇出

- **扇入：**多少模块直接调用我。
- **扇出：**我直接调用多少模块。

合理复用公共功能、避免一个模块协调过多对象；不是机械追求扇入最大、扇出最小。高内聚、低耦合贯穿概要设计和详细设计。

## 三、调整执行流程：减少不必要的工作

### 1. 你的真实改造

将反序列化逻辑提取到独立类，并将界面刷新调整为**全部样本读取完成后统一执行**。

### 2. 区分两条收益

- **职责拆分 → 修改影响范围更容易控制 → 可修改性收益。**
- **减少中间刷新 → 减少刷新开销 → 整体加载性能收益。**

不能仅凭代码拆分类就断言运行更快，也不能把整体加载提速等同于磁盘读取或解析算法本身提速。

## 四、评价结果：分清属性、指标和标准

### 1. 不同问题分别判断

**功能正确性**看结果是否正确；**性能**看速度和处理能力；**可靠性**看规定条件和时间内能否持续无故障；**可用性**看需要时能否提供服务；**可修改性**看修改成本与影响范围。

### 2. 故障发生与故障恢复不同

故障频率不变，恢复从 30 分钟缩短到 1 分钟，减少了不可用时间，改善可用性；不能据此说故障减少或可靠性提高。

### 3. 衡量有三个层级

**性能〔属性〕→ 响应时间〔指标〕→ 不超过 2 秒〔阈值〕。**

**回忆线索：先弄清要什么；一起变的放一起，各自变的分开；运行少做多余工作，评价分清关注什么、怎么量、怎样达标。**
