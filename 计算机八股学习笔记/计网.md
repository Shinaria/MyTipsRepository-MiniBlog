# 计网八股

## HTTP相关

### GET和POST作为请求时传递数据的一些区别

1. 传递数据时GET会把放在Line的URL里面,POST会把参数数据放在Body里
2. GET方法会有的限制:URL长度有限制;安全性.相比之下POST的传递能力受服务器处理能力和带宽限制
3. GET过的请求和结果会被缓存(比如浏览器的历史记录),POST的请求是不会被记录的

### (这种知识背景和情景下的)接口的幂等性是什么?

0. 判断条件:这个接口被二次请求后服务器状态是否发生了变化->没变就是幂等
举例:买东西下单,网卡了点了很多次请求
1. 生成了一堆订单->没有幂等性;只生成了一个订单->有幂等
2. 如何实现?请求时生成一个唯一的ID,服务器在缓存里查.

* 补充知识:生成订单发送请求的详细数据和ID可以以JSON格式塞在POST请求里面的Body里面

### 上一个举例的延伸问题:如何在一个超大的缓存里面查找这个ID有没有出现过?

1. 常见思路是用一些特化的数据结构存.
2. 引申知识->布隆过滤器,这是以一个位图形式存储的数据结构
3. 压缩率非常高,但是有一定的不可靠.

### 常见的HTTP状态码区别

* 502/504和500: 前者(502/504)是网关报的错,500是服务器报的错(比如服务器内代码执行出错)
* 400 Bad Request: 请求无效(语法错误或参数错误)
* 401 Unauthorized: 无身份
* 403 Forbidden: 有身份但无权限

### HTTP的"无连接"和"无状态"是什么意思?

* 这里的无状态和无连接并不能"望文生义"
* 无连接: 没有"保持"连接
* 无状态: 没有"身份"标记

### HTTP版本迭代是如何改善"无连接"的?

* 1.0时的问题: 情况下发送一个HTTP请求就需要TCP连接+断开一次,此为"无连接".

* #### 1. 第一步改善

* 1.1时Header里面有了Connection字段,使用Keep-Alive的方式进行了改善.
* TCP连接可以复用,但是先来先处理的排队机制会导致队头阻塞

* #### 2. 第二步改善 (HTTP 2.0)

* 1.x时期是文本传输,2版本时期改为二进制位传输
* **多路复用**->改为二进制传输后可以以类似时间片轮转的形式 **分帧传输** ,以此实现一个TCP连接的多响应请求的并发.
* 针对多个请求/响应使用**头部压缩**,减少传送.
* 1.x时期客户端必须先请求，服务器才能返回资源。2.0允许服务器在客户端未请求的情况下，**主动发送额外资源**。

### HTTP版本迭代是如何改善"无状态"的?

三个关键词: Cookie,Session,Token

* Cookie: 存储在用户本地,按照域名分类,这样有些信息
* Session: 存储在服务器,可用ID识别
* Token: 多个信息加密压缩后的字符串,可以用作跨域名传递信息.

### HTTPS为什么比HTTP更安全?

* 通信内容加密
* 需要第三方的可信机构颁发证书

### HTTPS的加密

* HTTPS = HTTP + tls/ssl
* 对数据加密: 防止数据被窃听
* 需要身份验证: 防止数据被篡改

### TLS的加密过程是什么样的?

* 简单概括: 通过非对称加密（公钥密码学）安全地交换随机数，共同生成一个只有双方知道的会话密钥，并验证身份。

#### TLS的握手步骤

1. 浏览器->服务器: 浏览器发起连接请求(Client Hello), 包含支持的TLS版本和密码套件列表, 一个ClientRandom(随机数)
2. 浏览器<-服务器: 服务器向浏览器回复响应(Server Hello), 消息包含选择的TLS版本和密码套件,一个ServerRandom(随机数),还有自己的数字证书
3. 浏览器->服务器: 浏览器验证证书, 通过后生成一个预主密钥(Pre-Master Secret), 用服务器公钥加密后发送给服务器
4. 服务器解密得到预主密钥, 再根据此前的ClientRandom和ServerRandom生成两边一致的对称会话密钥(Session Key)
5. 双方用会话密钥进行对称加密,客户端和服务器发送“Finished”消息, 确认握手成功

### HTTPS的证书有哪些信息?

* 服务器的域名
* 有效期
* 证书的签名,这个是由CA(证书颁发机构)用私钥生成,可以用来验证证书
* 证书颁发机构

### HTTP端口

http默认端口是80,https默认端口是443

## TCP

### TCP报文的结构

TCP报文主要也是由头部Header和数据Data组成

#### 头部结构

```pgsql
  0                15 16                               31 (位)
  +-----------------+-----------------------------------+
  |   源端口号(16)   |       目的端口号(16)              |
  +-----------------+-----------------------------------+
  |              序列号 (32)                            |
  +-----------------------------------------------------+
  |             确认号 (32)                             |
  +---------+-------+-----------+-----------------------+
  | 头部偏移 | 保留位| 控制位     |   窗口大小(16)        |
  | (4位)    | (6位)|   (6位)    |                      |
  +---------+-------+-----------+-----------------------+
  |     校验和(16)  |     紧急指针 (16)                 |
  +-----------------------------------------------------+
  |                选项(Options, 0~40字节)              |
  +-----------------------------------------------------+

```

#### 控制位有六位，分别对应

* URG：紧急指针有效
* ACK：确认号有效
* PSH：尽快推送到应用层
* RST：重置连接
* SYN：发起连接
* FIN：释放连接

### TCP如何实现可靠传输

* **数据校验**,参见报文结构的校验和
* 建立连接时生成一个**随机的序列号**,后续报文根据传送的数据大小递增
* 确认**应答机制**ACK, 收到数据/报文后需要回复ACK(客户端服务端都需要)
* **超时重传**机制, 一段时间没有收到ACK就会重传.
* 用**滑动窗口**控制传输的速率
* **拥塞控制**,用于试探传输速率的阈值(慢启动,拥塞避免,快重传,快恢复)
* 启动连接使用**三次握手**,结束连接使用**四次挥手**

### 四种拥塞控制算法的转换过程

#### 四种拥塞控制算法: 慢启动,拥塞避免,快重传,快恢复

名词解释:

* 慢启动: 以一种指数级增长的方式快速探测网络的可用带宽, 每经过一个RTT(往返时间)，拥塞窗口 cwnd就*2
* 拥塞避免: 拥塞窗口cwnd增长到慢启动阈值ssthresh时,每经过一个RTT, cwnd就+1, 避免引发拥塞.
* 快重传: 是针对网络波动情况下对数据报文的处理措施, 触发条件是数据发送方收到3个重复ACK
* 快恢复: 是针对网络波动情况下对拥塞窗口控制的策略, 降低拥塞窗口cwnd到新的阈值ssthresh(减半后加3), 然后直接进入拥塞避免(线性增加)阶段。

##### 几种算法使用的转换

* 慢启动->拥塞避免 : 拥塞窗口cwnd增长到阈值
* 慢启动/拥塞避免->快恢复 : 收到三个重复ACK(说明有数据丢失),触发快重传+快恢复
* 快恢复->拥塞避免 : 收到了一个新的ACK,说明重传成功,cwnd重新增长
* 任意状态->慢启动 : 开始连接/超时重传,cwnd从1开始每经过一个RTT指数增长一倍

几种状态切换时, 每经过一个RTT, cwnd的变动会随网络状态增加或减少, 宗旨是尽量试探当前网络状态的传输上限.

### 在**四次挥手**时, TIME_WAIT时间为什么是两个MSL?

背景解释:

* 当**主动关闭方**发送最后一个ACK(最后一次挥手)会进入 TIME_WAIT 状态
* MSL(Maximum Segment Lifetime)是报文在网络中最多能存活的时间。

原因:

* 时间大于1个MSL, 用于确保最后一个ACK能够到达服务器,而不是马上终止连接
* 时间等于2MSL而不是更久, 是为了防止端口被重新启用时有遗留的旧报文数据
* 这两点也是TIME_WAIT存在的原因(可靠地终止连接+旧连接的报文不影响新连接)

### UDP

#### UDP的报文

```bash
16位源端口号 16位目的端口 
16位报文长度 16位校验和
数据
```

* TCP主打可靠, UDP主打速度
* UDP无连接(不需要发起连接), 不可靠, 报文也不保证顺序, 仅有一个校验和保证数据正确
* UDP适用丢包不敏感的场景
* DNS,DHCP,RTP用的是UDP
* 如果需要保证UDP可靠性,只能在数据部分做文章,例如自行给数据加头尾然后自行做验证
