## 进程间调度·切换

### 常见的调度算法有哪些?

1. 先来先服务
2. 短任务优先
3. 最短完成时间优先
4. 时间片轮转(这个算抢占式)
5. 最高优先级调度(会提前为每个进程分配优先级)
6. 多级队列调度->多级反馈队列调度(进程可以在队列之间移动)

* 这几种算法可以按照是否有优先级(时间片轮转/其他的一些有优先级), 或者是按抢占式/非抢占式分类.
* 短任务优先和最短完成时间优先的区别是抢占式/非抢占式.

### 上下文切换的过程是什么样的?

* 上下文切换是指保存当前进程的状态(如寄存器, 程序计数器,内存映射等), 然后恢复另一个进程的状态.
* 切换的触发: 硬件终端, 异常, (进程请求)系统调用

1. 将旧进程的CPU寄存器状态保存至进程控制块PCB
2. 修改旧进程的PCB的进程状态(运行态->就绪态/阻塞态)
3. 根据调度算法选择下一个要运行的新进程
4. 从新进程的PCB中恢复寄存器快照至CPU
5. 修改新进程的PCB的进程状态为运行态

### 哪些情况下会导致内核态和用户态的切换?

1. 中断: 一个由硬件或软件产生的信号, 它通知CPU需要立即暂停当前正在执行的任务(硬件中断或软件中断)
2. 异常: 当CPU在执行用户态程序的指令时,检测到了一个错误或特殊条件(除零错误, 缺页, 调试断点)
3. 系统调用: 应用程序主动请求操作系统内核为其提供服务(创建进程, 读写文件, 申请内存, 网络通信)

#### 名词解释

* 内核态: 操作系统内核运行的状态, 可以执行所有指令, 访问所有硬件资源和内存.
* 用户态: 普通应用程序运行的状态, 权限受限, 如果想要主动访问系统资源需要通过系统调用.
* 硬件中断: 外部硬件设备主动发出的中断信号, 比如时钟中断, I/O中断, 外部输入中断
* 软件中断: 由程序主动触发的中断, 比如系统调用中断, 异常

## 内存

### 虚拟内存

虚拟内存是一种把磁盘的部分空间作为二级内存的一种技术

### 虚拟内存的好处是什么?

1. 可以给程序提供连续的,近乎无限的地址空间

### 页和页表

* 虚拟内存被分成一个个大小相等的块,称为“页”(page)
* 物理内存也分为同样大小的“页框”(page frame)
* 页表由进程控制块存储,记录虚拟内存到物理内存的映射

#### 常见的页大小

* x86/x64 架构: 在现代的Intel和AMD处理器中,通常每个页的大小为4KB.这意味着虚拟内存和物理内存都以4KB为单位进行分页.
* 大页(Large Pages): 除了常规的4KB页之外,一些架构还支持大页(large pages)或巨页(huge pages),通常大小为2MB或1GB.

### 页表的条目记录哪些东西?

1. 物理页框地址: 该条目映射的物理内存页框.
2. 有效位(Valid Bit): 指示该页表项是否有效,如果无效则说明该页没有被加载到内存中,可能需要从硬盘读取(页面置换).
3. 访问权限: 例如,是否只读,是否可写,是否可执行等.
4. 脏位(Dirty Bit): 指示该页是否被修改过,若修改过则需要将数据写回磁盘.
5. 引用位: 指示该页是否最近被访问过(用于页面置换).

### 逻辑地址到物理地址的转换计算

* 通常由CPU的MMU(内存管理单元)进行计算
* 也有"快表"作为高速缓存直接记录地址映射, 不用计算

### 缺页中断

* 当程序访问一个未加载到物理内存中的虚拟页时,会发生缺页中断.
* 操作系统需要选择一种页面置换算法来决定从物理内存中置换掉哪一页

#### 三种页面置换算法

1. FIFO 先进先出: 选择最早被加载到物理内存中的页面
2. LRU 最近最少使用: 选择最久未被访问的页面
3. 时钟算法: 根据一种算法选择

#### 时钟算法的步骤

* 把所有页面视作一个循环链表,操作系统维护一个指向当前页面的指针(像时钟的指针一样)。
* 每当发生缺页中断时,时钟指针会指向一个页面,查看该页面是否被访问过(通常通过设置一个**引用位**来标记是否访问过)。
* 如果该页面的引用位为1(表示该页面最近被访问过),则将引用位重置为0,并指向下一个页面继续检查。
* 如果该页面的引用位为0(表示该页面未被访问过),则替换该页面,并将其加载到内存中。

#### FIFO的优缺点

* 优点: 实现简单,易于理解
* 缺点: 效率较低, 因为并没有考虑页面的实际使用频率

#### LRU的优缺点

* 优点: 考虑了页面的访问频率
* 缺点: 实现复杂,需要额外的硬件或软件支持来记录页面的访问时间,会增加开销

## I/O模型

### 五种模型

1. 阻塞 I/O (Blocking I/O): 电脑执行程序时，等待用户敲键盘。没有输入前，它什么都不做，一直卡在“等待”状态。
2. 非阻塞 I/O (Non-blocking I/O): 电脑每隔几毫秒问一次：“键盘有按键输入吗？鼠标动了吗？”
3. I/O 多路复用 (I/O Multiplexing): 让操作系统统一帮忙“监听”多个设备。
4. 信号驱动 I/O (Signal-driven I/O): 键盘输入时直接向CPU发“中断信号”，CPU立刻暂停手头任务处理输入。
5. 异步 I/O (Asynchronous I/O, AIO): CPU与设备完全并行工作

### 阻塞 I/O(Blocking I/O)

* 工作方式: 应用程序发起 I/O 请求后,线程会被挂起,直到数据准备好并完成传输.
* 优点: 编写简单, 没有各种复杂的轮询和回调所以可靠性高
* 缺点: 效率低, 等待时不能做别的事; 扩展性差; 用户体验不好
* 举例: 系统调用read()
* 适用小规模场景: 一次性读文件; 写日志; 执行命令行工具

### 非阻塞 I/O(Non-Blocking I/O)

* 相比阻塞I/O而言, 没有数据的时候不会挂起线程, 而是设置一个标记(errno = EAGAIN 或 EWOULDBLOCK)
* 但是增加了"轮询开销": 需要反复检查数据, 运行逻辑增加而且浪费CPU资源.

### I/O 多路复用(I/O Multiplexing)

* 工作方式: 线程通过select, poll, epoll这三种系统调用监听多个I/O
* 为什么说它解决了阻塞 I/O 和非阻塞 I/O 的一些痛点？

### select

* 名称来源于系统调用的函数名select()

#### select的工作方式

* 应用把关心的 fd(文件描述符)放进 fd_set(一个位图).
* 调用 select() 后,内核扫描所有 fd,看哪些就绪.
* 返回后,应用再自己遍历整个 fd_set,找到哪些是可读/可写的.

#### 问题

* fd数量是有限制的(1024)
* 每次需要遍历整个fd列表

### poll

* 名称来源于函数名poll(), poll是轮询的意思
* 相比select使用一个**struct pollfd**存放所有fd
* 提升了1024的fd数量上限
* 但是轮询机制没有改变, 还是需要遍历整个fd列表

### select和poll的主要限制是什么？

* 这两种机制的性能开销会随着监控数量线性增长
* 缺乏状态变化机制和内核事件通知

### epoll - 关键词: 事件驱动

* Linux特有的机制
* epoll是event poll的缩写, 意思是"事件驱动的轮询"
* 目标是处理超大数量的连接: **高并发+高性能**

#### epoll的工作方式

* 应用调用 epoll_create() 创建一个内核维护的“事件表”, 通过 epoll_ctl() 注册/删除要关心的 fd.
* 内核自己维护这些 fd 的事件状态.
* 应用调用 epoll_wait() 时,内核直接返回有事件的 fd 列表.

#### epoll的两种工作模式

* 分为水平触发(LT)和边缘触发(ET)

#### LT(水平触发)

* 当一个 fd 的状态满足可读,epoll_wait()就会返回这个事件.只要条件还成立(比如缓冲区里还有数据没读完),下次 epoll_wait() 调用时,它还会再次返回这个事件.
* 语义类似select和poll, 编写简单
* 但是连续提醒会导致额外的系统调用开销, 性能低
* 适合不需要高并发的场景

#### ET(边缘触发)

* 当 fd 的状态从不可用变为可用时，epoll_wait()才通知一次.如果没有一次性把缓冲区的数据读光（或者写尽），内核也不会通知第二次.
* 因为只通知一次, 可以减少系统调用
* 但是应用必须在一次通知后把所有可用数据处理完, 不然会丢失数据
* 适用高性能网络服务器(Nginx,Redis)

#### 在epoll的ET模式下,如果一个事件没有被处理完,会发生什么？

* 剩余的数据会滞留在内核缓冲区, 如果缓冲区已满可能会导致连接中断
* 丢失事件, 导致程序出错
* 当收到一次可读事件时，要循环读取，直到read()返回**EAGAIN**或**EWOULDBLOCK**。

### 信号驱动 I/O(Signal-Driven I/O)

* 应用程序先注册一个信号处理函数，内核监视I/O, I/O就绪时给进程发信号，进程再在信号处理函数里去执行实际的 I/O 操作。
* 很接近事件驱动, 但是信号是异步触发的, 不易管理

### 什么是异步 I/O(Asynchronous I/O)？它和非阻塞 I/O 有什么区别？

* 应用程序发起 I/O 请求后立即返回，内核在后台完成操作，并在完成时通知应用程序（信号、回调等方式）。
